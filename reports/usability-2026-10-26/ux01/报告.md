## 2. 从零开始的实际操作顺序

1. 空资料打开后看到 Choose a server profile 与 Add server。检查了如何获取 API key 的说明，得知必须先在 Headscale CLI 创建管理凭据。填写本人入口和预备管理 key，通过实际密码控件设置加密密码并 Save and unlock。
2. 浏览总览零用户、零设备状态；从资料菜单切换简体中文。中文导航实际名称为概览、设备、用户、认证密钥、路由、访问控制，不存在独立 /settings 页面。
3. 添加 ux01-alice（显示名“新手 Alice”）、ux01-bob，搜索第二个用户、打开详情，再改名 ux01-bob-renamed。页面明确区分用户名是策略/CLI 引用，显示名和邮箱可选。
4. 创建 Alice 的默认单次密钥。默认可重复使用和临时设备均未勾选，到期为一周后。生成区提供安全保存提示、login-server 和真实 tailscale up 命令，且明确尚未验证任何设备已注册。
5. 初次共享 capture-key 工具错误捕获列表里的截短值，导致客户端提示 key too short。这是工具问题而不是产品发错 key。使用本人私有脚本只从已生成密钥区域读取完整可见值并私存后，client-a 正常注册；没有打印完整密钥或截取生成密钥画面。
6. 创建 Bob 的可重复密钥，client-b 正常注册，同时广告本人隔离目标 10.42.0.2/32 与出口路由。两台设备获得 100.64.0.1、100.64.0.2。client-a 经真实 Tailscale HTTP 代理访问第二台的 8081，返回 ux01-client-b。
7. 在设备页查看详情、搜索 client-a、改名 ux01-laptop。在用户删除对话框确认 Alice 尚有一台设备，因此删除按钮禁用并列出该设备；取消退出。
8. 访问控制创建团队 ux01-team，将 Alice 加入，声明 ux01-app 标签并授予团队客户端申请权。检查策略、完整原文审阅、发布，随后刷新并解锁读回。过程中记录发布后仍保留“未保存任何内容”检查提示的问题。
9. 路由页实际批准隔离 /32 路由；client-a 接受路由后取得 ux01-subnet-target。撤销同一路由后请求超时，证明不是 Kubernetes 直连。默认出口两条路由也实际成对批准/撤销，但出口目标访问持续超时，详见网络表，不记通过。
10. 删除两条默认放行规则，检查并发布空 ACL；同一 client-a→100.64.0.2:8081 请求由成功变超时。通过页面规则编辑器添加 *→*、端口 *，审阅发布后，同一请求重新成功。另创建 ux01-discard-me 团队草稿，使用放弃更改及确认真正丢弃。
11. 声明第二标签 ux01-keep，设备编辑器审阅完整双标签集合并确认个人身份转换。随后移除 app，保留 keep，服务器接受写入。选中全部可用标签时出现“无兼容定义”误导提示，但实际标签集合可以正常写入。
12. 使用恢复个人身份入口，在真实设备清除广告标签并启动不带预认证密钥的强制重新认证，取得真实短时请求。通过目标用户、对外 login-server 和可信通道确认后，UI 批准并仅读取当前状态：原节点 ID 1、原 IP、Alice 用户、空标签集合一致，旧 preauth 关联不再显示；实际 HTTP 仍成功。保留了恢复读回截图。
13. 进一步进行带 tag:ux01-app 请求的 keyless 强制重新认证；通过普通添加设备→注册待审批设备流程批准。真实 Headscale CLI 读回 user=tagged-devices、tags=[tag:ux01-app]，证明团队 owners 的实际客户端申请路径有效，不只是 UI 保存。
14. 在线标签维护选择现有 keep 身份，并点击检查设备标签，却只打开只读详情；关闭后返回访问控制，再开维护目标已丢失。重试确认后，使用正常设备菜单→编辑标签手工完成 app→keep 替换，HTTP 访问成功。清除真实客户端旧 app 广告，移除旧申请授权并发布。退役检查仍给合并式阻塞提示；之后从正常删除标签入口移除无使用的旧策略定义并发布，没有将它冒称为完整退役。
15. 服务器设置创建一把新的管理 API key，只撤销新建非当前 key，页面与独立 CLI 均显示到期时间已变更。执行带复选确认的 Backfill，结果为无需任何更改。
16. 修改本地资料密码；旧密码明确失败，新密码解锁成功。打开第二个真实标签页验证共享解锁；保持另一页开启时刷新不丢会话；单页退出同步让两页进入锁定状态。
17. 切换深色主题并验证移动布局。输入含空格的 bad username!，页面明确给出用户名不能包含空格或控制字符；改为 ux01-temporary 后创建成功，再删除无设备的临时用户，完成失误恢复闭环。
18. 使 Bob 可重复注册密钥过期，再删除；两次操作之后现有 client-b 均仍可访问。最终通过 UI 移除 client-b，随后 Bob 用户变为零设备并可正常删除。
19. 下载真实设备 CSV：364 bytes、两条记录，字段为 name、owner、status、addresses、tags、advertisedRoutes、approvedRoutes、lastSeen、expires，未发现 hskey-auth/API key 内容。
20. 最后实际清除全部本地资料，双方标签页锁定且配置卡消失。独立 CLI 仍读到 Alice、ux01-laptop、keep 标签及团队/ACL，证明未删除服务端数据。另一标签页继续提示输入资料密码，但已没有任何资料卡，记录为恢复文案问题。

## 5. 新手体验观察与正面证据

- 注册密钥与管理 API key 分在不同入口；注册密钥创建区明确说明尚未验证设备注册，比“生成成功即完成接入”的暗示更可靠。
- 用户删除保护列出真实设备并禁用操作，原因可理解；设备移除后同类用户确实可以删除，流程闭环。
- 完整策略审阅、完整标签集合审阅、个人身份转换复选确认，以及不带预认证密钥的恢复说明，均在实际操作中有帮助。
- 团队/标签弹窗部分说明仍说点击完成、顶部保存，而真实按钮为保留在策略草稿中、发布所有策略更改；这属于额外的术语不一致观察，未单列高严重度问题。
- 退役检查在无设备、无邀请、owners 为空、已确认外部依赖后仍仅给出合并式阻塞说明，本参与者无法判断是哪一类条件尚未满足；记录受阻，不据此断言退役判断算法错误。
