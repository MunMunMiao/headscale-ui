## Chrome 独立性与环境限制

10 个本机原生 Google Chrome `155.0.8059.85` 进程分别使用互不相同的 `--user-data-dir` 和仅绑定 loopback 的 CDP 端口 9411—9420；已读回各自 CDP `/json/version` 并检查 PID/profile 唯一性。

为避免十个窗口干扰宿主桌面，浏览器以 `--headless=new` 运行。它们是真实 Chrome 渲染、持久化 profile、SharedWorker、Web Crypto 与 IndexedDB，不是十个标签页或一个浏览器的十个临时 context。但这不等于真人观察、真实触摸设备或真实 OS 剪贴板交互。

局域网 HTTP 不是安全上下文，无法满足本项目 SharedWorker/WebCrypto 契约，因此入口使用 HTTPS NodePort。本轮生成仅供实验的短期证书：

- 证书未装入宿主机或系统信任库；
- 每个临时 Chrome 仅通过该证书的 SPKI pin 信任本轮证书，不使用全局 `--ignore-certificate-errors`；
- 真实 Tailscale 客户端仅在所属 Pod 挂载测试证书并通过 `SSL_CERT_FILE` 读取；
- UX01 初始空资料页已验证 `isSecureContext === true`、SharedWorker 为 function、crypto.subtle 和 IndexedDB 可用，控制台无页面错误。

## 网络真实性与隔离

- 每位成员两个官方 Tailscale daemon，采用 `--tun=userspace-networking`，不是假节点或直接写数据库。
- 没有 privileged、hostNetwork、hostPath/TUN 挂载、NET_ADMIN 或宿主网络修改。Nginx 使用正常镜像所需的默认容器权限并移除 NET_RAW；其余容器 drop ALL。
- NodePort 入口仅授权本次局域网使用；NetworkPolicy 允许同 namespace 和 `10.0.0.0/24` 来源进入普通测试服务。
- 专用目标 Pod 的 ingress 只允许所属 `client-b`，不允许 `client-a` 直连；避免把 Kubernetes 直连成功误当作 Tailscale 转发成功。
- 子网路由只通告本人的目标 `/32`，不通告真实 LAN 或整个集群网段。
- Userspace 可以验证真实 TCP/UDP、子网和出口转发；不能据此宣称内核全 L3、任意协议、吞吐或物理设备兼容性已覆盖。

## 部署阶段的设施问题（不计入产品缺陷）

| 问题 | 原始证据 | 修正与验证 |
| --- | --- | --- |
| 大 ConfigMap 的 client-side apply 注解超过 256 KiB | `metadata.annotations: Too long: may not be more than 262144 bytes` | 改用 server-side apply，不再把压缩前端包复制进 last-applied 注解。 |
| 切换 apply manager 后自己的旧字段冲突 | `.spec.containers[…].resources.limits.cpu` 所有权冲突 | 仅对本次唯一命名、带归属标签的资源接管字段；未触及现有 namespace。 |
| 默认 socket 目录无法创建 | `setting up unix socket: creating directory failed with permission error: /var/run/headscale` | 实验 Headscale unix socket 改到所属可写数据目录。 |
| 将 Nginx 所有 capabilities 移除导致镜像正常启动失败 | `chown("/var/cache/nginx/client_temp", 101) failed (1: Operation not permitted)` | 恢复正常容器默认权限，仅 drop NET_RAW；无 privileged/宿主权限。 |

以上修正后部署命令退出码 0，40 Pod 全部就绪，10 套 `/api/v1/user` 与 `/version` 独立只读验证通过。
