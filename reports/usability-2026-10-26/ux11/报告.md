# UX11 独立管理员真实使用报告

## 1. 结论

本轮从空浏览器资料、空 Headscale 用户/设备/策略开始，实际执行了共同基线，再完成邮箱 principal 歧义与真实 Tailscale SSH check 专题。全部管理操作经本人原生 Chrome 中的渲染控件完成；没有读取业务源码、已有测试或其他成员报告，没有派生子代理，没有修改项目实现、测试、共享 helper 或宿主权限。

最重要的已确认问题是：**UI 正常创建一个与既有策略 principal 同邮箱的新用户，可以在策略文本完全未改的情况下，使原本可用的既有连接失效。** 两个独立创建/删除周期均复现；不同邮箱用户的创建/删除不影响连接；目标服务在失败期间持续健康。UI 的策略检查明确返回 `multiple users found`。这不是仅凭“邮箱可重复”推测出的风险。

真实 SSH 专题结果分层如下：

- **真实 action=check 请求产生、UI 批准、目标消费批准：通过。** 目标日志确认 `access granted`。
- **另一条真实请求的 UI 拒绝、客户端收到拒绝：通过。** 客户端为 `tailscale: access denied`，退出 255。
- **批准后真正执行远程命令：受阻，未通过。** 客户端为 `operation not permitted`、退出 1；目标容器所有有效/允许/边界 capabilities 均为 0。没有扩权、修改宿主或用伪造请求替代。
- SSH check 策略由正常 Headscale CLI/gRPC 作为**实验设施**准备，不计作 UI 策略编辑能力；所有批准/拒绝决定均在 UI 中作出。

子网 `/32` 路由有完整真实数据面对照：审批前失败、审批后 HTTP 200、撤销后失败，且目标健康、客户端 A 的 Kubernetes 直连始终失败。出口路由完成 UI 审批/撤销，但已审批且选择出口后的隔离目标访问超时，**没有宣称出口数据面通过，也没有据此判定 UI 缺陷**。

## 3. 从空环境开始的实际操作顺序

以下按实际先后顺序记录；“成功”只指该项说明的层级，不代表其所有边界均已验证。

### 3.1 建档、用户与真实接入

1. 首次打开进入 `Choose a server profile`，显示没有任何连接资料；没有通过内部状态跳过首次登录。
2. 打开 Add server，输入本人 origin、管理 API key 与加密密码，保留 Remember 默认勾选；点击 **Save profile**，随后选择保存的资料并输入密码解锁。
3. 总览显示用户、设备、可用注册密钥和待审批路由均为 0。保存空总览证据。
4. Users 中创建 Alice 与 Bob，分别填写不同用户名、显示名及测试邮箱。查看 Bob 详情，看到用户 ID、0 台设备、无有效注册密钥及无个人设备。
5. 将 Bob 的用户名从 `ux11-bob` 改为 `ux11-bob-renamed`；显示名和邮箱保留，列表读回新用户名。
6. Auth keys 中创建 Alice 的默认单次 key：默认到期约一周、Reusable 未选、Ephemeral 未选。仅经安全捕获保存到本人私有文件。
7. 用这把 UI 产生的 key 接入真实 `client-a`，获得 `100.64.0.1`；UI 后续将 key 显示为 Used、不可用于正常新注册。
8. 单标签刷新后资料重新锁定，页面明确解释没有其他标签保留解锁状态；重新解锁。打开第二标签后不再要求输入密码，验证共享会话。
9. 为 Bob 创建 Reusable key，接入真实 `client-b`，初始地址 `100.64.0.2`；由真实客户端广告本人 `/32` 和 IPv4/IPv6 默认出口路由。
10. 查看 A 的设备详情，验证节点 ID、所属用户和地址；按实际搜索框搜索 `client-a`，结果为 1/2，再清除筛选。
11. 将 A 显示名称改为 `ux11-laptop`。真实默认数据面 A→B:8081 返回 HTTP 200，B 本机服务健康。

### 3.2 路由和访问策略基线

12. Routes 中看到 B 的 `10.42.0.43/32`、`0.0.0.0/0`、`::/0` 均待审批。
13. 审批前实测：A 直接访问隔离目标失败，经 Tailscale 代理访问也失败；B 直接访问目标为 HTTP 200。
14. UI 审阅并批准单条 `/32`；真实代理流量变为 HTTP 200，而 A 的直接访问仍失败。CLI 独立读回 approved/subnet route。
15. UI 批准出口路由，确认 IPv4/IPv6 作为一对审批；在 A 正常选择 B 为出口后访问隔离出口 Service，实际超时；B 对同一 Service 为 HTTP 200。没有为此改宿主或加权限。
16. UI 撤销出口对，并在 A 取消选择出口；再撤销 `/32`。真实子网访问恢复失败，B 健康仍为 HTTP 200，CLI 不再显示 approved routes。
17. Access controls 中从隐式全放行开始，创建团队 `group:ux11-ops`，通过用户选择器加入 Alice。实际组成员 principal 是 `ux11-alice@example.com`。
18. 定义 `tag:ux11-server` 与 `tag:ux11-secondary`；给运维团队配置服务器标签的 client authorization，并添加 SSH 端口及自定义端口 8081 的网络规则。
19. 点击 Check policy，明确返回检查通过但未保存。打开完整发布审阅，查看原始/拟提交的完整策略，再发布。
20. 刷新读回组、标签、owners 与规则。原有隐式全放行被明确保留为 IPv4/IPv6 ACL；没有误把定义标签当作自动收紧网络。

### 3.3 标签、设备、凭据和本地资料基线

21. 在 B 的 Edit tags 中选择服务器与辅助两个标签，审阅完整集合并确认个人身份转标签身份的提示，实际提交。UI 保持结果弹窗，说明写入确认不等于连接验证。
22. 打开 Restore personal identity，阅读非 authkey 重新认证、备份通道、明确目标用户及请求归属核验的要求；此时先保留标签继续维护检查。
23. 从 Access 的 Live tag maintenance 打开 Migrate identity，填写现有辅助标签目标并使用 Review device tags 入口。该入口进入设备详情；关闭后回到 Access。未把此步骤记为完成整套自动迁移。
24. 从 Machines 的实际 Edit tags 入口移除 `tag:ux11-server`，审阅完整目标集合仍保留 `tag:ux11-secondary`，提交后读回成功。
25. 对服务器标签运行 Retirement check：当前设备引用已为空，但仍有 `acls[2].dst[0]` 策略引用，页面阻止宣称可以退役；没有勾选未实际核实的外部部署确认。
26. 在 B 真正运行清空 advertised tags 的 `tailscale up ... --force-reauth`，产生真实短期请求。通过 Restore personal identity 表单选择 Bob、核对真实请求及公开登录 origin，经 UI 批准。
27. UI 明确读回原设备身份、空标签和 Bob；CLI 独立核对 ID 2、IP `100.64.0.2`、Bob 所属关系与 CLI 注册方式，恢复个人身份成功。没有用未打标签的 authkey 冒充恢复。
28. 对仍有 A 的 Alice 打开删除确认，UI 列出 `Devices: 1`、设备名称及组引用，并禁用 Delete；取消，未绕过保护。邮箱搜索 Bob 得到 1/2。

31. Maintenance 中打开 Backfill 确认，勾选全服地址范围提示后在本人环境执行，结果 `No changes were needed`。
32. Encryption 中阅读“清除所有资料”的范围，打开确认后取消；未实际删除全部本地资料。
33. 修改本资料密码，两个标签均锁定；旧密码解锁被明确拒绝，新密码可以解锁。随后实际 Log out，两个标签均显示跨页退出说明，再用新密码解锁。

37. 创建无设备临时用户 `ux11-cleanup`，通过正常删除确认清理，用户列表回到 2/2。
38. 创建 `ux11-discard` 团队草稿，点击 Discard changes 并确认，草稿消失且没有发布。
39. 在真实 B 上尝试 `tailscale up --advertise-tags=tag:ux11-server`；命令接受，但当前注册节点未变为标签身份。按官方说明，这是注册时生效的参数，未把普通 up 接受命令记为标签申请成功。真正授权注册在第 3.6 节补齐。

至此共同基线的各项目均已实际尝试；出口数据面、完整新标签迁移及真正远程 shell 等未通过项均保留其边界，未用浏览页面替代操作成功。

### 3.5 真实 SSH check 专题

49. B 上正常执行 `tailscale set --ssh=true` 成功。A 原来没有系统 ssh；只在本人一次性 A 容器安装正常 OpenSSH 客户端。未装宿主包，未改项目依赖。
50. 在已有 TCP 22 网络允许规则下，真实 `tailscale ssh root@100.64.0.3 ...` 返回“tailnet policy does not permit”，证明网络端口规则不等于 Tailscale SSH 会话授权。
51. 经 UI 将 B 分配为 `tag:ux11-server` 身份。作为实验设施，通过正常 `headscale policy set --file /dev/stdin` gRPC 路径，在旧策略上仅增加真实 `ssh` check 规则；没有使用直连数据库或 debug auth request。
52. A 再发起真实 `tailscale ssh`，daemon 产生实际检查链接，客户端保持等待。进入 Add device → Register pending device → Request type `SSH check`，经 secret 参数填写该真实链接，点击 Approve SSH check。
53. UI 返回 `SSH check approved.`，目标日志在该决定后确认 `access granted` 并启动会话；随后实际命令启动失败，客户端 `operation not permitted`、退出 1。有效/允许/边界 capabilities 全为 0。停止远程命令执行分支，没有加权限或更换宿主模式。
54. 新建第二条真实 SSH 请求，只测试无需启动 shell 的拒绝路径。在同一 UI 中提交 Reject SSH check，UI 返回 `SSH check rejected.`，客户端为 `tailscale: access denied`、退出 255。未重试已批准的 shell，也未绕过权限限制。

## 5. 已确认问题

### UX11-F01：正常创建重复邮箱用户，使既有邮箱 principal 策略歧义并中断原连接

- **严重程度：高。** 普通已授权管理员的常规用户创建会影响既有流量及后续策略检查/发布；未发现或声称未经授权访问。
- **分类：已确认跨功能集成缺陷。** 依赖 Headscale 对邮箱 token 的唯一解析契约；未读取源码，因此不把具体实现责任未经验证地归到某一函数或单一组件。

#### 前置条件

1. Alice 与 Bob 的用户名、邮箱均不同，A 归 Alice、B 归 Bob。
2. 通过 Access 用户选择器将 Alice 放入 `group:ux11-ops`，实际策略成员为 `ux11-alice@example.com`。
3. 没有开放网络规则，明确允许该组到 B `100.64.0.3:22,8081`。
4. A→B:8081 和 B 本地健康检查都已经是 HTTP 200。

#### 复现步骤

1. 在 Users → Add user 输入未使用过的 username、任意显示名，Email 填 Alice 已在用的 `ux11-alice@example.com`。
2. 正常点击 Create user；不要编辑 Access，也不要变更客户端或目标服务。
3. 用同一 A、同一 B IP、同一 TCP 8081 发出新的 HTTP 请求，并同时检查 B localhost:8081。
4. 在 Access 点击 Check policy。
5. 通过 UI 删除刚创建的无设备重复邮箱用户，不修改策略，重发原请求。
6. 重复一轮；另用不同邮箱用户创建/删除作反证对照。

#### 预期

是否允许重复邮箱，应由产品业务契约决定，**不是预设所有同邮箱创建都必须被后端拒绝**。但当该邮箱已作为正在使用的策略 principal，且创建会令其解析歧义时，UI 应在提交前识别并明确阻止或解释具体影响，让管理员作有信息的选择，或采用可稳定唯一解析的身份表达。至少不能只报告创建成功，却在未修改策略的情况下静默破坏现有连接。

#### 实际

- 创建成功，Users 显示 3/3；不同 ID、不同 username 使用同一邮箱，没有正在使用的策略影响提示。
- 原连接从 HTTP 200 变为超时；第一周期连续两次失败，第二周期再次失败。
- 同时 B localhost:8081 全部 HTTP 200，内容始终 `ux11-client-b`。
- 原策略文本完全不变；第二周期及无关邮箱对照的原文 SHA-256 均为：

  `5a050ae0a3d4f08b9f4cabdaeaa5fc54bb24c4445cdb72d600b28b0c4d839f9b`

- UI Check policy 的实际错误为：

  ```text
  validating policy user references: multiple users found:
  token "ux11-alice@example.com" found:
  [ 1: ux11-alice, 6: ux11-alice-duplicate2, ]
  ```

- 删除新重复邮箱用户后，没有策略清理勾选项、没有策略编辑、没有客户端重连，连接恢复 HTTP 200，策略检查重新通过。
- 不同邮箱用户创建/删除时连接始终 HTTP 200，削弱了“任何用户写操作或偶发网络波动导致故障”的替代解释。

#### 影响

- 建立用户的管理员未必正在操作 Access，也未必知道邮箱是策略 identity。
- 已发布策略与 UI 成功提示会造成“策略没改，设备突然不通”的排障困难。
- 当前实验证明的是既有允许关系失效和策略检查失败，没有证明权限扩大、持久数据损坏或所有网络流量均中断。

## 6. 体验观察（与功能缺陷分开）

### UX11-O01：用户创建文案与实际策略 principal 不一致

- **程度：中。** 是认知与影响提示问题，与 F01 相关，不另算一个独立断网根因。
- Add user 文案称：`Policies and the Headscale CLI refer to this user by the user name. Display name and email are optional.`
- 但通过 Access 的正常用户选择器加入组，完整发布审阅实际写入邮箱，而非用户名。用户名可改而邮箱相同会导致 principal 消歧失败。
- 预期是清楚区分 CLI 注册所用 username 与 Access 实际选用的 principal，并说明重复邮箱会影响已使用的策略。证据见首次完整策略审阅、Add user 的可访问树及 F01 实验。

### UX11-O02：网络规则中的“SSH”与 Tailscale SSH check 的关系不够易发现

- **程度：中，体验观察，不认定网络端口规则实现错误。** 标签访问区的 SSH 选择实际生成 TCP 22 规则，不会自动生成 Tailscale `ssh` 会话授权。
- 实测在网络 22 允许后，真实 SSH 仍返回 tailnet policy does not permit；准备独立 `ssh.action=check` 后才产生检查请求。
- 本次在可见 Access 管理流程中没有找到创建/编辑 SSH action 的入口，因此为专题使用了明确标注的正常 CLI 实验设施。没有据此断言源码中不存在任何相关功能。
- 预期是能清晰解释“允许 SSH 端口”与“允许 Tailscale SSH 登录/检查”的区别，并为管理员提供可发现的配置指引。

### UX11-O03：SSH 决策表单没有展示请求主体摘要

- **程度：低至中，易用性/安全确认观察。** 填入真实 SSH 检查链接后，界面只给 Approve / Reject，没有展示来源身份、目标设备和本地登录用户名摘要；相比恢复个人身份流程的明确用户与请求核验提示，管理员对自己将批准什么缺少页面内反馈。
- 本次请求由本人可信 CLI 通道取得，因此没有误批；也没有证明服务端允许任意修改请求目标。不能把这条观察升级为已证实的越权漏洞。

### 正向观察

- 标签覆盖显示完整目标集合、加/减差异和个人身份转换，实际保留其他标签的行为可验证。
- 个人身份恢复没有把空标签更新或无标签 key 当成万能修复，而是引导真实非 authkey 重新认证，并要求备份管理通道。
- 全策略审阅会检测外部变更；本次实际拦住了一次会遗漏 SSH 设施字段的过期发布，刷新重试后保留该字段。
- 注册 key 与现有设备退役的区别、出口路由成对审批、Backfill 全服范围、改密跨页锁定均有明确说明。
- Check policy 文案明确“检查通过不等于保存/运行/连接验证”，没有把本次检查当数据面成功。

## 7. 真实网络与 SSH 输出摘录

完整原始脱敏输出见 [ux11-network.txt](evidence/ux11-network.txt)、[ux11-ssh.txt](evidence/ux11-ssh.txt)、[ux11-identity.txt](evidence/ux11-identity.txt)。以下只摘录判断所需信息。

### 7.1 子网路由

同一来源 A、同一目标 `10.42.0.43:8081`，通过 daemon 的 HTTP 代理访问：

| 阶段 | A 直接访问目标 | A 经 Tailscale 代理 | B 直接访问目标 | 独立路由读回 |
|---|---|---|---|---|
| 未审批 | Connection refused | HTTP 502 / exit1 | HTTP 200，`ux11-subnet-target` | 仅 available，无 approved |
| UI 审批 `/32` 后 | 仍 Connection refused | HTTP 200 / exit0，`ux11-subnet-target` | HTTP 200 | approved/subnet 含 `/32` |
| UI 撤销后 | Connection refused | download timed out / exit1 | HTTP 200 | 无 approved |

实际代理命令形态为：

```sh
http_proxy=http://127.0.0.1:1056 wget -T 7 -S -O - http://10.42.0.43:8081/
```

A 直连始终失败，避免将 Kubernetes 原生连通当作 Tailscale 子网转发。只有审批后的那一阶段计作真实子网数据面通过。

### 7.2 邮箱专题同源同端口对照

所有下列请求均是 A→`100.64.0.3:8081`，非旧地址 `.2`。测试窗口没有客户端重连、目标切换或策略编辑。

| 操作/阶段 | 真实连接 | B 本机健康 | 旧策略 |
|---|---|---|---|
| 明确组允许规则发布 | 200 / exit0 | 200 | 已建立基准 |
| 创建同邮箱用户，第一周期 | 两次超时 / exit1 | 两次200 | 未变 |
| 删除该用户，第一周期 | 两次200 / exit0 | 两次200 | 未变 |
| 创建不同邮箱用户 | 200 / exit0 | 200 | 同一 SHA-256 |
| 删除不同邮箱用户 | 200 / exit0 | 200 | 同一 SHA-256 |
| 创建同邮箱用户，第二周期 | 超时 / exit1 | 200 | 同一 SHA-256 |
| 删除同邮箱用户，第二周期 | 200 / exit0 | 200 | 同一 SHA-256 |

成功响应实际包含：

```text
HTTP/1.1 200 OK
Content-Length: 14
ux11-client-b
```

失败实际包含：

```text
Connecting to 127.0.0.1:1056 (127.0.0.1:1056)
wget: download timed out
command terminated with exit code 1
```

之后的 SSH 设施策略和 Bob owner 增加发生在邮箱对照结束以后，不属于“不改策略”窗口，没有混入对照。

### 7.3 真实 SSH check

实验设施增加的 SSH 部分为：

```json
{
  "ssh": [
    {
      "action": "check",
      "src": ["group:ux11-ops"],
      "dst": ["tag:ux11-server"],
      "users": ["root"],
      "checkPeriod": "always"
    }
  ]
}
```

这是正常策略配置，不是生成待审批请求的 debug 方法。短期链接均经 secret 参数输入，报告和证据不保留完整链接。

真实客户端在两条连接中均输出检查提示：

```text
# Headscale SSH requires an additional check.
# To authenticate, visit: [REAL_SSH_CHECK_URL_REDACTED]
# Authentication checked with Headscale SSH.
```

最后一行不能单独证明管理员已批准，因此本报告以 UI 决定、目标日志和终止结果共同判断。

**批准分支：**

```text
UI: SSH check approved.
Target: access granted to ux11-alice@example.com as ssh-user "root"
Target: starting non-pty command ... --cmd=echo ux11-real-ssh-round-1
Client: operation not permitted
UX11_SSH_EXIT=1
```

没有 `ux11-real-ssh-round-1` 的成功远程输出，故不能称远程命令执行通过。

**拒绝分支：**

```text
UI: SSH check rejected.
Client: tailscale: access deniedConnection closed by UNKNOWN port 65535
UX11_SSH_EXIT=255
```

第二条连接没有尝试创建远程 shell；它验证的是拒绝决定由真实客户端消费。

## 8. 环境、工具及上游边界

### UX11-L01：批准后 SSH 命令启动受限

- `tailscale set --ssh=true` 和真实 check 握手都可以运行，不能笼统写成“userspace 完全不支持 SSH”。
- 批准后目标确实尝试启动 Tailscale 的 SSH child，随后客户端 `operation not permitted`、退出 1。
- 目标 root 进程的有效/允许/边界 capabilities 全为 0。当前证据支持“在受限环境中远程命令启动受阻”，但没有定位唯一失败系统调用，因此不武断声称只需某一个具体 capability 即可解决。
- 没有增加 `CAP_SETUID`、`CAP_SETGID`、`NET_ADMIN`、privileged 或 hostNetwork，没有修改宿主 TUN/路由，也没有用另一个环境冒充成功。远程命令、PTY、非 root 登录及文件传输均未继续测试。

### UX11-L02：出口数据面未成功，归因未知

- UI 出口成对审批与撤销成功，A 接受选择 B 为出口。
- 对隔离 Service 的代理请求超时，而 B 到同一 Service 健康；说明目标不是未启动。
- 没有完成出口审批前后/撤销后的完整成功链，未证明真实出口转发。当前限制可能涉及 userspace 路由或设施路径，但没有足够证据归到某一层；不列为 UI 功能 bug。

### UX11-L03：工具错误不计作产品问题

本轮出现的以下错误都先修正定位/用法再继续，没有作为产品缺陷：

- 空 Auth keys 页有两个同名 Create auth key 控件，transport strict-mode 报不唯一；选择工具栏第一个后成功。
- 曾猜测 `Search machines...`，实际控件名是 `Search by name, owner, tag, version...`；改用真实标签后搜索通过。
- 成功标签提交会保留结果弹窗、来源详情关闭会返回 Access、移除规则会先出现确认；过早点击背景导航或后续菜单的 timeout 属于脚本预测错误，不是业务失败。
- `lab.py --help` 不受设施脚本支持；只读查看设施接口后使用正常操作。
- Tailscale 1.102.5 的 `set` 没有 `--advertise-tags`；按 CLI 帮助改用 `up`，并依据官方注册语义进行真实重新认证。
- 文档抓取工具出现额度/服务错误，之后用 curl 只读读取公开官方文档。未修改任何工具认证或凭据。
- 单次 viewport 设置未随所有 CDP 断连持续保留；以实际 DOM 读回及 PNG 尺寸报告环境，不据此认定 UI 布局 bug。
