# ux04 独立管理员实际使用报告

## 1. 结论

本成员从空浏览器资料开始，完成了服务器资料配置、两位用户和两台真实客户端接入，并跨越成员、设备、注册密钥、策略、路由、管理密钥和本地会话实际操作。成员专题中，重名保护、有设备用户删除保护、无邮箱用户改名时 group/tagOwners 引用迁移、无设备用户删除时引用清理均获得真实 UI 与独立读回证据。

确认一项高严重度功能问题：当既有策略已经通过邮箱标识用户时，正常“Add user”允许无警告创建相同邮箱的新用户，随即使既有用户的实际访问失败，并使后续正常策略发布因 principal 歧义被拒绝。第二轮只做“创建重复用户→实际探测→删除重复用户”，未提交任何策略修改，仍复现失败和恢复，因此不是定位器错误或失败策略提交本身造成的假象。

另有两项低严重度体验观察，分别为 principal 说明不一致、CSV 缺少稳定的用户名/用户 ID。出口数据面、真实客户端标签申请授权判定、SSH check、完整标签身份迁移等未完成项单独列出，不记为通过。

测试结束时，本成员创建的数据对象和本地加密资料已清理；namespace、Chrome 等设施仍须由协调者按本轮约定统一删除。本报告不宣称“所有设施已经删除”或“覆盖全部未知场景”。

## 3. 从零到一的实际操作顺序

1. 首次打开入口，页面显示没有连接资料。打开 Add server，填写资料名、Server URL 和管理 API key，设置资料密码，保持 Remember this connection 默认开启，通过 Save and unlock 进入 Overview。空总览用户、设备、注册密钥和待审批路由均为零。
2. 从 Users 创建 Alice Member（用户名 ux04-alice，有邮箱）和 Bob Member（用户名 ux04-bob，有邮箱）。再次创建同用户名 ux04-alice 时，表单标记无效、显示 A user with this name already exists，创建按钮禁用。取消后按邮箱搜索成功，再查看用户详情。
3. 从 Auth keys 为 Alice 创建默认一次性、非 ephemeral 的注册凭据，为 Bob 创建可重复、非 ephemeral 凭据。默认到期约一周。通过实际页面显示的完整凭据分别接入 client-a/client-b；B 同时广告本人目标 /32 和双栈出口路由。两台实际节点分别获得 100.64.0.1、100.64.0.2。
4. 初次 helper 捕获密钥误取了表格遮罩摘要，首次 join 报 key too short。仅在本人私有脚本中改为读取 Auth key created 区域的完整 code 后正常恢复；共享 helper 和产品代码未修改，此事不计产品缺陷。
5. 在 Machines 搜索并查看 A 详情，将其显示机器名改为 ux04-alice-laptop，实际尝试在线筛选。进入 Alice 删除确认，有一台设备时显示设备清单并禁用 Delete user，取消恢复正常页面。
6. 在 Access controls 新建 group:ux04-ops，选择 Alice；创建 tag:ux04-service，为其添加团队和 Alice 直接客户端申请授权。检查策略，通过完整原始前后对比审阅发布。界面实际生成邮箱 principal alice-ux04@example.test。随后 Alice 改名为 ux04-alice-renamed，邮箱 principal、设备归属和组/tagOwners 引用仍有效。
7. 在 Routes 审批本人 /32；真实探测从未审批失败变为成功，撤销后再次失败，同时普通 peer 访问仍成功。也实际审批和撤销双栈出口路由，选择出口后的隔离目标访问未成功，保持为未解决项。
8. 在 Access 删除默认全放行规则，检查并发布明确 acls:[]。A 对 B 同一 8081 HTTP 请求从成功变超时，B 本机服务仍返回正确内容。随后通过页面新增 group:ux04-ops→100.64.0.2:8081 并发布，实际请求恢复成功，证明邮箱组 principal 在用户名改名后仍能生效。
9. 创建第二个标签 tag:ux04-keep。通过设备 Edit tags 对 B 审阅完整集合、确认个人身份转换影响后分配两个标签。独立读回显示 Tagged Devices 身份及两个标签。之后只移除 service 标签，独立读回确认 keep 保留。
10. 浏览 Live tag maintenance 的迁移入口、注册入口停用说明和退役检查。仍有设备时退役被阻断，未把定义删除等同全局退役。
11. 从 Restore personal identity，实际在 B 清空 advertised tags 并执行非 authkey --force-reauth，得到真实短期注册请求。通过可信管理通道核对后，在 UI 选择 Bob、填写经确认的 public login-server、逐项确认并批准。读回显示 B 恢复 Bob 个人身份、标签为空、无 authkey 关联；本次 ID 2 和 IP .2 保留，HTTP 再次成功。该次结果不外推为所有恢复都会保留 ID/IP。
12. 进入资料菜单 Server settings，创建非当前会话管理 API key，随后使其到期并删除，最终独立读回仅剩最初环境管理 key。查看 Backfill 风险说明并实际勾选确认提交；本次没有构造需要增删 IP 的 fixture，后续节点地址读回保持正常。
13. 修改资料密码后，页面要求用新密码解锁；旧密码实际拒绝，新密码成功。新标签页共享解锁，存在兄弟页时刷新保持会话，任一页 Log out 使两个标签页同时锁定，单页重新解锁后两页恢复。另切换简体中文、英文和深色主题。
14. 新建无邮箱、无设备 Cleanup Member，加入组和 tagOwners；完整审阅显示 principal 为 ux04-cleanup@。改名为已有 ux04-bob 时禁用保存；换为 ux04-cleanup-renamed 后，审阅将两处引用同步改成新 username@。发布后独立读回正确。删除该无设备用户时默认勾选同步引用清理，审阅确认仅移除该用户，读回保留 Alice 引用，既有连通性仍成功。
15. 让 A 到期，真实客户端变为 NeedsLogin、SelfExpired=true；从 UI Disable expiry 后变回 Running，实际 HTTP 恢复。检查一次性 key 的 Used 状态和可重复 key 使用后仍 Ready 的状态，实际使可重复 key 到期并删除。
16. 创建重复邮箱用户并实际复现问题，随后通过正常删除恢复；第二轮未做策略写入再次复现并恢复，详见 F01。
17. 真实下载成员 CSV 并独立解析；同连接验证 375×812 成员页 scrollWidth=375。离线 helper 场景曾尝试，但时序未充分验证，恢复联网后不计通过。
18. 最终通过 UI 移除 B、A，删除用过的一次性 key，删除余下用户并清理邮箱引用，删除空团队与标签定义并发布空策略。清除所有本地资料，两个标签页锁定；关闭本人新建的第二个标签页。最终独立读回 users/nodes 为空，groups/tagOwners/acls 均为空。

## 5. 已确认功能缺陷

### ux04-F01：无警告创建重复邮箱会破坏正在使用的邮箱 principal

- 严重程度：高（P1），成员正常操作可使已经获准的实际连接中断，并阻塞后续策略维护。
- 类型：UI/Headscale 集成使用流程缺陷。Headscale 允许目录中存在重复邮箱是观察到的上游行为；本项问题是管理界面在自己生成并使用邮箱 principal 后，仍允许无警告创建会使该 principal 歧义的用户。没有通过源码确定内部根因，不声称已完成安全漏洞审计。
- 前置条件：Alice 和 Bob 分别拥有 A/B；通过 UI 创建 group:ux04-ops=[alice-ux04@example.test]，并发布该组到 B:8081 的放行规则；A 的真实 HTTP 请求成功。
- 最小复现步骤：
  1. Users→Add user，使用新的合法用户名和相同邮箱 alice-ux04@example.test。
  2. 创建成功，界面没有指出邮箱正在被策略引用或会变成歧义。
  3. 不修改策略，从 A 经 Tailscale HTTP proxy 再访问同一 B:8081。
  4. 删除刚创建的无设备重复邮箱用户，再做同一请求。
- 预期：在创建前识别正在使用的邮箱 principal 冲突，并阻止无意破坏或提供明确、安全的冲突处理。正常新增目录用户不应悄悄切断无关既有连接。
- 实际：创建后同源同端口请求超时；B 本机目标仍返回正确内容；删除重复用户后请求恢复。第二轮创建/删除之间没有提交策略修改。原始 policy get 前后未改变。
- 额外结果：第一轮尝试把重复用户加入组时，完整发布被拒，明确报 multiple users found: token alice-ux04@example.test，并列出两个用户。界面再显示写入结果未知的长说明；没有给出“重复邮箱→删除或消歧”的直接恢复指引。
- 数据面证据：UTC 17:03:32 的 collision-repro-no-policy-write 超时，紧接的 collision-repro-service-alive 返回 ux04-client-b；UTC 17:03:51 的 collision-repro-delete-restored 返回 ux04-client-b。
- 恢复：通过 UI 删除新建、无设备的重复邮箱用户即可，不需要 CLI 修改策略、重启服务或改数据库。已完成恢复。
- 影响范围限制：实际证明的是本测试 A→B:8081 以及相关策略发布受影响；没有证明所有 tailnet 流量都会中断，也没有证明权限提升。
- 证据：E02、E03、E04、E05，以及完整 UI 轨迹 E01。

## 6. 体验观察

### ux04-O01：principal 说明和界面生成值不一致

新增用户说明表示策略和 CLI 按用户名引用用户，但团队/标签授权选择器实际优先使用唯一邮箱，没有邮箱时才使用 username@。初次管理员容易把显示名、用户名、邮箱和策略身份混为一谈；重复邮箱问题更难在创建前预判。建议说明明确区分这几个字段，并展示当前采用的策略 principal。本项为低严重度理解成本观察，与 F01 相关，不单独升级为安全问题。

### ux04-O02：CSV 丢失管理中使用的稳定身份字段

真实成员 CSV 只有 name,email,provider,machines,joined。name 实际是 Alice Member/Bob Member 等显示名，没有用户名 ux04-alice-renamed/ux04-bob，也没有用户 ID。下载成功且两行均可解析，但仅凭导出表不能直接关联 CLI/策略用户名。同显示名或缺邮箱时会更难辨认；本次没有进一步制造同显示名恢复错误，因此不宣称数据丢失。建议导出明确的 display_name、username 和 user_id 字段。

## 7. 真实客户端与网络验证

所有阳性都要求读到预期正文，不以客户端命令退出 0 代替连通性。最初 tailscale nc 的 stdin/EOF 路径出现退出 0 但无正文，已排除为“通过证据”；后续采用实际 tailscaled HTTP proxy 127.0.0.1:1056 发出 wget 请求。
