# 独立模拟用户端到端体验：研究设计

## 目标与边界

- 使用至少 10 名独立 AI 模拟用户，不能等同于真人用户研究或统计抽样。
- 每位成员从空白 Chrome profile、独立 namespace 和独立 Headscale 数据开始，体验所有适用的用户可见功能，再完成一个不同的深入探索方向。
- 主要经由正常 UI 操作；环境准备、真实 Tailscale 客户端命令与独立验证必须与用户操作区分。
- 不修改业务代码、不提交、不推送、不使用真实业务数据。不把源码推测计为运行时缺陷。
- 所有成员报告位于本目录；不写进实现目录、测试用例目录或特定成员的工作区。
- 测试结束删除本次临时 namespace、Service、客户端、配置、凭据、Chrome 进程和 profile、临时脚本；仅保留报告与经过脱敏的必要证据。

## 基线与资源调配

- Git 提交：`4d21dd98c97055ba8e77aa9e2e42659d82478de5`，开始时工作区干净。
- kubeconfig 仅用于连接，不修改其内容；context：`home`。
- 单节点：30 CPU，165025608 KiB 内存（约 157.4 GiB），Pod 上限 110。
- 初始活跃 Pod 57；初始使用约 3.9 CPU、53.8 GiB 内存。
- 本机：10 CPU、32 GiB 内存；Chrome 155.0.8059.85；复用项目已有 Playwright。
- 初始规划每人一个控制平面 Pod、两个真实 Tailscale 客户端 Pod、一个仅供本次验证的目标服务 Pod。10 人新增 40 Pod，保留至少 13 个调度槽。
- 根据实际负载、Pending/OOM 和本机内存调整并发；不按集群总内存盲目增加成员。
- 真实客户端优先 userspace/netstack，无 privileged、hostNetwork、宿主机 TUN 挂载或宿主机路由修改。
- LAN NodePort 使用独立测试凭据；TLS、浏览器信任和网段访问限制在实施后记录，不隐瞒测试环境特殊配置。

| UX08 | 凭据管理员：邀请密钥创建、消费、重复、到期与撤销 |

初始十人之外，依据覆盖缺口增加 UX11、UX12，总计十二名。已完成 UX03、UX04 的运行环境后再建立补充环境，避免无控制地累加资源。UX12 的第二服务器用于真实跨服务器隔离验证，不用同一后台别名替代。

每人共同流程：首次访问及连接 → 建立成员和必要策略 → 通过 UI 产生注册所需凭据并接入真实客户端 → 管理设备、成员、邀请、标签、策略、路由 → 验证刷新和持久化 → 处理取消/失败和依赖 → 清理用户数据。实际不存在的功能不虚构；未完成项必须列为未测/受阻，不写作通过。

## 外部场景来源

1. [Headscale policy](https://headscale.net/stable/ref/policy/)：允许/拒绝、tagOwners、autogroup、实现限制。stable 会随时间变化，执行以实际部署版本为准。
2. [Headscale routes](https://headscale.net/stable/ref/routes/)：子网路由审批、出口节点、autoApprovers 与 ACL 组合。
3. [Headscale registration](https://headscale.net/stable/ref/registration/)：交互注册与 preauth key 两条入口，个人设备与带标签设备。
4. [Headscale issue 3212](https://github.com/juanfont/headscale/issues/3212)：出口节点与 autogroup:internet 曾发生回归；作为场景来源，不预设本版本有缺陷。
5. [Tailscale userspace networking](https://tailscale.com/docs/concepts/userspace-networking)：真实 userspace 客户端、SOCKS5/HTTP 代理。
6. [Kernel vs userspace routers](https://tailscale.com/docs/reference/kernel-vs-userspace-routers)：userspace 支持真实 TCP/UDP 路由与出口，不等价于完整 L3 内核路由或压力测试。
7. [Tailscale exit nodes](https://tailscale.com/docs/features/exit-nodes)：广告、控制端审批和使用端选择必须同时成立；验证真实流量而不只看 UI。

研究保留定向工作流与自由探索两部分。不能声称穷尽所有未知场景；最终列明未测范围和阻塞。

## 单人成员报告要求

每位成员必须自己编写报告，包含：角色和任务、实际浏览器/环境标识、按顺序的操作记录、功能覆盖与结果、遇到的问题、预期/实际、复现步骤、脱敏证据、严重程度、恢复情况、未完成项。区分已复现缺陷、体验观察、基础设施/上游限制与待确认项。

## 汇总与验收

- 至少 10 份独立成员报告。
- 按功能/阶段的覆盖矩阵，每个通过项对应操作或实际输出。
- 问题去重但保留原报告引用；高影响问题独立复核。
- 真实设备注册、策略允许/拒绝和路由/出口结果单独说明。
- 最终清理审计：namespace 数、临时 Chrome 进程/profile、临时配置凭据和本地容器产物。
