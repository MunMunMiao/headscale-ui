# UX12 独立管理员真实使用报告

## 1. 结论

本次从空 Chrome profile、空主后台开始，完成了共同基线的实际操作，并在同一 UI Origin 内使用了两台真正独立的 Headscale 服务器。**未发现已知管理凭据发往错误服务器、实体串服、旧确认框跨服执行或一次性密钥结果跨服残留。** 多标签页共享登录、退出和切服的行为与界面说明一致。

确认的主要问题是：第二服务器为 `policy.mode=file` 且没有 `policy.path` 时，删除无设备、无有效密钥的用户，仍默认启用无法执行的策略清理，并以空列表声称存在策略引用，导致普通用户删除先被禁用；取消该勾选后可以正常删除。另记录了标签退役检查的阻塞原因不可定位、迁移入口不能直接进入标签编辑器两项工作流体验问题。

子网路由完成了真实数据面的“未批准不可通 → 批准后可通 → 撤销后不可通”。策略限制通过新的 Tailscale TCP 连接验证了允许、拒绝与恢复阳性对照。出口路由审批与撤销的控制面通过，但出口数据面的一次尝试超时，不能记为通过。标签设备恢复个人身份使用了真实、无预认证密钥的重新认证请求，经过 UI 审批、读回和连通性检查。

本报告不是源码审计，也不是全量自动化测试结论。只浏览、只收到写入确认、受到阻塞和未执行的分支均单独标明。

## 3. 从 0 到 1 的实际流程

### 3.1 主服务器共同基线

1. 首次打开只有“Choose a server profile”和空资料提示。通过真实表单添加 `UX12 Primary A`，输入 A 的 URL、API key 和配置密码，使用“Save and unlock”进入概览；概览的用户、设备、可用密钥和待审路由均为 0。
2. 从菜单切换简体中文。建立 `ux12-a-alice`、`ux12-a-bob`，设置可区分的显示名称和测试邮箱；搜索 Bob、打开详情，将其用户名改为 `ux12-a-bob-renamed`。
3. 在认证密钥页创建默认一次性密钥，以及属于 Bob 的可重复使用密钥。默认过期时间约为 7 天，“可重复使用”“临时设备”均未勾选。密钥只保存于本人的私有临时文件，然后让两台真实客户端接入。
4. UI 和 Headscale CLI 均读到两台设备：`client-b` 为 Node 1 / `100.64.0.1`，`client-a` 为 Node 2 / `100.64.0.2`。一次性密钥使用后在筛选中显示“已使用”；可重复使用密钥使用后仍可用于新注册。
5. 搜索 `client-a`，打开设备详情并重命名为 `ux12-a-laptop`。尝试删除仍有该设备的 Alice，UI 列出设备并禁用删除按钮。稍后通过 UI 使设备过期，再禁用过期，列表重新显示在线、从不过期。最终在该客户端已转移至 B 后，通过 UI 移除 A 中的旧设备记录。
6. 在访问控制中建立 `group:ux12-a-ops`，加入 Alice；建立 `tag:ux12-a-server`、`tag:ux12-a-keep`，为 server 标签配置组拥有者以及 8081 访问规则。执行“检查策略”，审阅完整前后 JSON，再发布。随后单页刷新触发锁定，输入密码后返回 `/access`，已发布定义仍在。
7. 为 `client-b` 分配 server、keep 两个标签，检查完整集合及个人身份变化警告后确认。在线维护读到两个现有标签。再建立 v2 标签，尝试维护页迁移；入口落到了只读设备详情，因此改用设备菜单中的“编辑标签”，将完整集合改为 keep + server-v2，经差异审阅后写入，保留无关 keep 标签。该次迁移保存有 UI 写入确认和完整目标集合证据，未另存迁移瞬间的 CLI 快照，也未单独验证迁移后的 ACL 流量。
8. 使用“恢复个人身份”入口，通过 `client-b` 的可信管理通道运行清空公布标签、强制重新认证且不携带预认证密钥的真实客户端命令。把真实请求填入 UI，明确选择 Bob、核实 login-server 和请求来源，再批准。点击“仅读取当前状态”后，UI 确认预期用户、空标签集合及原设备身份一致，旧认证密钥关联不再显示。新的 TCP HTTP 请求双向均得到 200。
9. 实测策略限制：先取得双向 HTTP 阳性；移除广泛允许规则，仅保留组到 server 标签 8081 的授权。新的 TCP 连接显示 Alice→标签设备 200，反向发起连接超时；两端本地 HTTP 服务一直健康。恢复广泛允许规则后，新的 TCP 连接双向再次 200。
10. `client-b` 真实公布隔离目标 `/32` 和 IPv4/IPv6 默认出口路由。UI 单条批准、撤销子网路由，完成了真实前后对照；默认出口路由也成对批准与撤销。一次出口服务探测超时，已恢复客户端“不使用出口节点”。
11. 服务器设置中创建并使一把非当前会话 API key 过期，当前管理会话继续可用。维护页检查 Backfill 说明和确认，实际执行，结果为“无需任何更改”。
12. 稍后删除没有设备的 Alice，看到其组引用与清理选项；用户删除之后出现完整策略清理审阅，继续确认后组成员清理成功。该流程的跨资源提交不是本次验证过的事务；没有把它报告成原子删除。

### 3.2 真正独立的第二服务器与状态隔离

1. 在第二个原生 Chrome 标签页打开主 UI，直接共享 A 已解锁会话。一个页面保留未提交用户表单，从另一个页面退出；两个页面均锁定，表单被移除。
2. 在原 UI Origin 中添加 `UX12 Secondary B FILE`，使用 B 的独立 key 解锁。两个标签页都切换到 B，而地址栏仍为主 UI Origin。
3. B 的用户和设备初始为空。通过 UI 创建 `ux12-b-carol`、`ux12-b-dave`，后者改名为 `ux12-b-dave-renamed`。B 的 Access 明确说明 file 模式、path 为空、无法编辑；Members 中“加入用户组”和“允许通过客户端申请标签”被禁用。
4. 在 B 正常创建属于 Carol 的一次性注册密钥。将真实 `client-a` 从 A 登出，用 B 的 UI 密钥加入 B，命名 `ux12-b-traveler`，随后通过 UI 改名为 `ux12-b-server-only`。B 此设备恰好也是 Node 1 / `100.64.0.1`，与 A 的 Node 1 数字和地址碰撞，但后台确实独立。
5. 分别读取 A/B 的全部六个页面，另用独立 Headscale CLI 读回：A 有 Alice/Bob 和 A 的设备，B 有 Carol/Dave 和 B 的设备；没有用同后台别名充当两台服务器。
6. 保留 B 的一次性注册密钥结果，从另一页退出并解锁 A；结果消失，A 的密钥列表恢复为 A 自己的两条记录，连接命令没有继续显示 B 的地址或秘密。
7. 在 A 一页保留未发布团队草稿，另一页打开 A Node 1 的移除确认。退出并切换 B 后，草稿提示已丢弃，旧移除框不在；B Node 1 仍存在，没有因为数字 ID 相同而被删除。
8. 在 B 的服务器设置中创建非当前会话 API key，结果仍打开时从另一页切换 A。设置弹窗被关闭；重新打开 A 设置只显示 A 的 API key 列表，不显示 B 的一次性结果。后续回 B 将新 key 设为过期。
9. A 修改配置密码后，共享会话立即锁定。旧密码被拒绝，新密码可以解锁 A；B 仍能用原环境密码解锁，验证了密码修改的资料范围。
10. B 删除无设备、无有效密钥的 Dave 时遇到 F01。取消默认策略清理勾选后删除成功，B 其他用户与设备继续可用。
11. B 只改配置名称即可保存，不需要重新输入 key 和密码。再尝试编辑为无效 key，UI 拒绝且保留原有可用连接；关闭后仍可正常解锁。另用已确认无监听的本人 loopback 端口 `https://127.0.0.1:59422` 和无效占位 key 测不可达连接，得到网络/CORS 排障提示；继续编辑、关闭并确认丢弃后回到原资料。
12. 从 B 的 Carol 菜单打开 `/devices?user=1`，然后切到 A。重新解锁后返回的是 `/devices`，原 B 用户 ID 筛选被清掉，未把 B 的用户名保留在 A 内容中。
13. 测试在途写入：A 用户创建点击返回后约 0.2 秒，在另一标签页退出并解锁 B。浏览器记录该 A POST 被中止，但独立读回确认后台 A 已创建 `ux12-a-race-write`；B 没有该用户。回到 A 经 UI 删除了这个无设备用户。**请求中止不代表服务器未提交；也没有观察到向 B 重发。**
14. 真实下载用户、设备 CSV，检查行数和字段，没有发现完整密钥或已知配置凭据。
15. 在登录页删除 B 的单份本地资料，A 仍保留并可解锁；随后正常重新添加 B。最后清除两份本地资料，两个标签页均不再有资料卡；语言、主题也恢复英语/系统。后台用户、设备与管理 key 没有被这次本地清除删除。

| B `/devices?user=1`，切 A | 回到 `/devices`，B 用户筛选被清除 | 数字 ID 碰撞没有保留错误用户标签 |
| A 创建用户后立即从另一页退出/切 B | A 请求在浏览器被取消，B 页面不出现旧创建结果 | A 后台可能已提交：本次确实已提交；B 无该实体，且无向 B 重发 |
| 删除 B 单份资料 | A 卡片保留，仍能解锁 A | B 后台仍有 Carol 和真实设备 |
| 最终清除全部本地资料 | 两页无资料卡，共享会话锁定 | A/B 后台用户、设备及管理 key 仍存在 |

### 请求隔离证据

捕获时间为本地约 01:44—02:04（原始文件使用 UTC 的 2026-10-25 17:44—18:04）。捕获不是整个会话的全量网络日志。

- 总计 1,224 个请求事件，其中 1,174 来自 SharedWorker，50 来自页面。
- 615 个请求携带 A 的已知管理凭据，545 个携带 B 的已知管理凭据；这 1,160 个请求中，**凭据与目标 Origin 错配为 0**。
- 14 个 OTHER 凭据事件对应本人的无效占位 key/不可达连接实验，未保存其值；50 个 NONE 为无该类凭据的页面请求。
- 抓到的非 GET 请求为 6 POST、5 DELETE、3 PUT，目的后台与 UI 当时选择的服务器一致。
- 57 个 HTTP 500 全部是 B 的 `/api/v1/policy` 读取。B 的 CLI 也明确返回从空 path 读取策略失败；这是本次只读模式前置环境的已知表现，不计作 A 的业务故障。
- 6 个 401 全部来自 B 的无效 key 编辑实验；7 个 `ERR_CONNECTION_REFUSED` 来自本人的 loopback 不可达实验。294 个 `ERR_ABORTED` 主要伴随退出、锁定、切服和页面读取取消，不能笼统当成产品异常。

在途创建的关键时序（UTC）：

1. `18:02:22.059`：A 凭据向 A `/api/v1/user` 发出 POST。
2. `18:02:22.229`：请求因退出在浏览器中中止。
3. `18:02:22.266`：共享退出操作返回。
4. `18:02:22.574`：B 解锁点击返回。
5. 独立读回：A 有 `ux12-a-race-write`，B 没有；后续 A 的 UI DELETE 正常清理它。

这里验证的是请求与结果隔离，不是“退出可回滚已经发送的写入”。

## 6. 问题清单

### UX12-F01：只读策略模式使无依赖用户删除默认陷入不可执行的策略清理

- **分类 / 严重程度：**已确认界面逻辑与文案缺陷，中等（可绕过，不是后台不支持删除）。
- **前置：**B 为 file-mode 且 path 为空；Dave 无设备、无有效认证密钥；没有可读取、可编辑的策略文件。
- **复现：**用户 → Dave 操作 → 删除用户。
- **实际：**对话框显示“以下策略条目引用了该用户”，但引用列表为空；同时展示 file-mode 无 path 的错误说明，默认勾选“同时从这些策略条目中移除该用户”，删除按钮禁用。
- **恢复验证：**取消该勾选后，删除按钮启用；纯用户删除请求返回 200，列表及独立后台读回确认 Dave 已删除。
- **预期：**区分“存在策略引用”与“无法读取/修改策略”。该场景应明确提供用户独立删除路径，而不是默认选中不能执行的策略清理并声称存在引用。
- **影响：**普通管理员容易误以为整个服务器只读，或认为必须修改服务器模式才能删除空用户；阻塞一项本来可以正常执行的非策略操作。
- **证据：**`evidence/ux12-secondary-delete-blocked-default.png`、`ux12-secondary-delete-workaround.png`；`ux12-ui-key-transitions.json`；请求汇总中的 B `/user/2` DELETE。

### UX12-F02：标签退役检查没有给出可定位的具体阻塞项

- **分类 / 严重程度：**已确认的工作流反馈问题，中等；不能据此断言后台退役判断算法一定错误。
- **前置：**A 的 keep 标签已不在设备上，没有匹配邀请和其他显示出的策略引用。真实个人身份恢复后进入其“在线标签维护 → 退役检查”。
- **复现：**刷新所需数据源，等待完成，再确认“外部部署负责人已核查……”；展开最新策略读回结果。
- **实际：**设备、邀请、策略引用区域没有列出依赖，外部确认已勾选，仍只显示“当前设备、注册入口、策略引用、未知来源或尚未确认的外部部署阻止了退役”。未说明到底是哪一类、哪个对象、哪个数据源或哪项确认在阻止继续。
- **预期：**即使需要保守阻止，也应列出具体未满足项及重新核验方式，不能只把所有可能原因并列给用户猜。
- **影响：**无法判断是仍有真实依赖、数据未核验，还是界面本身没有更新，导致无法完成有意义的退役确认。
- **恢复与范围：**普通标签删除入口可完成“仅移除策略定义及列出的引用”，已审阅并发布 keep 定义删除；该入口明确声明不代表全局退役，本报告也没有把它当成完整退役成功。
- **证据：**`evidence/ux12-retirement-no-visible-dependency-blocked.png`；`ux12-ui-key-transitions.json`；最终 policy 中 keep 定义已移除。

### UX12-F03：迁移预览后的“检查设备标签”落到只读详情，不能在该流程继续编辑

- **分类 / 严重程度：**已确认的工作流衔接问题，较低至中等；有手动恢复路径。
- **前置：**A 设备同时有 keep、server；已发布 server-v2 定义。
- **复现：**server 的在线标签维护 → 使用现有身份 → 输入 server-v2；看到 keep + server → keep + server-v2 的正确预览；点击“检查设备标签”。
- **实际：**进入 `/devices?node=1&popup=node&from=access`，弹窗只有设备详情与关闭，没有标签编辑动作。关闭后回 Access，需要重新进入设备列表的操作菜单，手工删除旧标签、添加目标并保留其他标签。
- **预期：**能继续进入包含完整目标集合的编辑/审阅步骤，或至少明确说明下一步如何进入编辑器。没有要求不经确认自动迁移。
- **影响：**用户离开已校准的迁移上下文后重新操作全量标签集合，增加遗漏其他标签或混淆目标的机会。
- **恢复验证：**从设备菜单编辑完整集合，保留 keep、替换为 v2，经差异审阅及写入确认完成操作；随后真实恢复个人身份。
- **证据：**`evidence/ux12-tag-migration-preview.png`、`ux12-tag-migration-detail.png`、`ux12-ui-key-transitions.json`。

### 体验观察，不与已确认的后台功能缺陷混计
