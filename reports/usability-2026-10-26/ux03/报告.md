## 一、结论

两台真实 Tailscale 客户端均成功接入，设备管理员的核心专题已实际完成：设备到期与禁用到期、设备改名、管理员标签身份转换、客户端申请标签，以及两台设备分别通过无 authkey 的真实重新认证恢复个人身份。身份恢复后，不仅 UI 显示正确，还独立核对了 Headscale 节点记录、真实 daemon 状态与 HTTP 连通性。

共同基线已逐项实际尝试。访问策略完成同源同端口的允许—拒绝—恢复对照；子网路由完成批准成功、撤销失败、重新批准成功的真实数据面闭环。出口路由的控制面审批与撤销成功，但出口数据面持续超时，不能记为通过。

确认一项标签迁移交接流程缺陷，以及退役检查解释不足、标签选择提示矛盾两项体验问题。未读取源码或其他成员报告，不推断实现根因，不把 helper 定位错误或 CLI 参数错误算作产品缺陷。

## 三、从零开始的实际顺序

1. 首次打开为空白资料选择页，没有保存的服务器资料。通过 Add server 填入本人的服务器地址、管理 API key、资料名称与加密密码，使用 Save and unlock 进入控制台。明确区分浏览器连接资料与 Headscale 用户。
2. 浏览空总览与用户页，创建 ux03-alice / Alice Personal、ux03-ops / Linux Operations 两个用户。个人用户使用 example.test 测试邮箱，没有真实个人信息。
3. 在 Auth keys 创建个人用户单次密钥，确认默认有约一周有效期，Reusable 和 Ephemeral device 均未勾选。创建 Linux 用户可重复密钥。经实际 UI 取得完整凭据后接入 client-a 和 client-b；后者同时广告本人的 /32 子网及 IPv4、IPv6 默认出口路由。
4. 设备页出现两台在线设备。通过真实客户端状态确认 BackendState=Running、正确 IP 与对端在线；经 Tailscale HTTP 代理访问另一端 8081，返回 ux03-client-b。
5. 查看个人设备详情，尝试 bad name ! 被明确校验拒绝，再保存合法名称 ux03-alice-laptop。实际使用搜索和 Online 筛选，结果为 1 / 2。
6. 用户详情显示个人设备与用户 ID。尝试删除仍有设备的 Alice Personal，确认删除按钮禁用且列出阻塞设备。把用户名称改为 ux03-alice-renamed，并通过 Headscale users list 独立读回确认。
7. 在 Access controls 创建团队 ux03-admins、设备标签 ux03-server 与 ux03-managed，为团队加入 Alice，授权该团队通过客户端申请 server 标签；另外配置团队到 server 标签的 8081 访问规则。检查策略、审阅完整 before/after、发布。刷新导致单标签页资料锁定，重新输入资料密码后，团队、标签与规则仍存在。
8. 令个人设备 Expire。真实 daemon 转为 NeedsLogin、Expired=true，访问相同 100.64.0.2:8081 超时。通过 UI Disable expiry 后，daemon 恢复 Running、KeyExpiry=null，HTTP 恢复成功。
9. 给 Linux 服务器赋予 managed+server 双标签。完整审阅明确提示将移除个人归属，勾选确认后写入；CLI 读回用户变为 Tagged Devices，标签集合正确。
10. 完成路由控制面与真实子网数据面对照；尝试真实出口数据面但失败，保留为未通过。所有网络操作仅使用本人隔离目标。
11. 删除开放访问规则及精确标签访问规则，发布显式 acls:[]，相同客户端到相同 8081 端口超时。随后只恢复 group:ux03-admins → tag:ux03-server:8081，HTTP 再次成功。
12. 从 Live tag maintenance 为 server 创建空迁移目标 server-v2，完整发布。迁移入口多次只打开只读设备详情，无法交接到设备编辑器。使用普通 Machines 行菜单手工替换 server→server-v2，保留 managed；写入后原精确访问失效，证明没有隐式复制旧标签权限。
13. 使用 Restore personal identity 为 Linux 服务器发起真实无 authkey 重新认证。真实客户端产生短期 Auth ID / 链接；通过受信任管理通道取得，页面明确选定 ux03-ops，核对 public login-server 与请求归属后批准。UI 与 CLI 均读回原 Node ID 2、原 IP、用户 2、空标签及 CLI 注册方法。恢复开放实验策略后，真实 HTTP 成功。
14. 个人客户端通过正常 tailscale up 和真实重新认证请求申请已授权 server 标签，页面批准后实际成为标签身份。再从 Restore personal identity 清除广告标签、发起另一真实无 authkey 请求，明确选定用户 1 并批准；读回原 Node ID 1、原 IP、空标签、ux03-alice-renamed，HTTP 成功。
15. 创建又丢弃一个临时团队草稿，确认未留在已发布策略中。创建非当前会话管理 API key 并使其到期，当前会话不受影响。执行 Backfill，实际结果为 No changes were needed。
16. 轮换资料密码，旧密码被拒绝，新密码可以解锁。打开第二标签页，确认共享已解锁会话；另一标签页存在时刷新仍保持登录。单页 Log out 导致两页同时锁定。实际切换简体中文、英文及深色主题。
17. 查看清除全部本地资料确认，确认作用对象为本浏览器所有资料，并取消。该操作未真正执行，不声称已删除浏览器本地数据。
18. 创建仅标签身份、可重复的 server-v2 注册密钥，通过维护入口查看精确匹配密钥并删除停止该已知入口。两台设备已恢复个人身份、该注册入口已删除、策略无引用后，退役检查仍泛化阻塞。使用明确的“仅移除策略定义与列出的引用”路径完成定义删除与发布，不能等同完整退役通过。
19. 在删除前保存真实客户端、路由与网络探测证据。通过 UI 删除 client-b，独立读回节点 2 与路由已消失；随后删除无设备用户 ux03-ops，独立用户列表只剩用户 1。
20. 为排除单设备偶发现象，在剩余 client-a 上重新赋予 managed+server 双标签，选择现有 managed 作为迁移目标。来源已验证且预览目标去重为 managed；点击 Review device tags 再次只打开只读详情，未进入标签编辑。保存前后截图后结束研究，最后两标签页均退出锁定。

## 五、已确认问题

### UX03-F01：迁移入口没有把目标集合交接到设备编辑流程

- 严重程度：中。属于核心标签维护流程中断，有正常绕行路径；没有观察到静默错误写入或数据丢失。
- 前置条件：已发布两个标签定义；设备拥有 managed+server；标签维护来源校验已完成。
- 复现步骤：Access controls → server 的 Live tag maintenance → Use an existing identity → 输入 managed → 等待预览显示 managed,server → managed → 点击 Review device tags。
- 预期：进入可审阅完整目标集合的设备标签编辑器，仍需用户显式确认；不应自动写入。
- 实际：导航到 /devices?node=1&popup=node&from=access，弹出只读 Machine details，仍显示原双标签，唯一按钮为 Close。目标集合没有进入设备编辑流程。client-b 的 server→server-v2 和 client-a 的 server→managed 均复现。
- 恢复：关闭详情后进入 Machines，用行菜单 Edit tags 手工构造完整目标集合、保留无关标签、审阅并确认。client-b 通过此路径成功迁移。
- 证据：/Users/munmunmiao/Documents/web/headscale-ui/reports/usability-2026-10-26/ux03/evidence/20-migration-source-and-target.png；/Users/munmunmiao/Documents/web/headscale-ui/reports/usability-2026-10-26/ux03/evidence/21-migration-handoff-details-only.png；/Users/munmunmiao/Documents/web/headscale-ui/reports/usability-2026-10-26/ux03/evidence/09-migration-opens-details-not-editor.png。

### UX03-F02：退役检查没有解释真正剩余的阻塞条件

- 严重程度：中。确认为用户可见的体验阻塞，不推断后端根因。
- 前置条件：server-v2 曾用于实际设备；之后设备已通过非 authkey 重新认证恢复个人身份；唯一标签注册 key 已删除；该标签没有 ACL 或其他可见引用，owners 为空。
- 复现步骤：打开其 Retirement check，Refresh required sources 并等待完成，展开 Latest policy readback，确认观察列表为空，再勾选外部部署依赖已核实。
- 预期：给出具体的剩余来源或阻塞对象；若来源无法核实，应明确指出哪一个来源，不能只罗列所有可能性。
- 实际：设备、邀请、策略引用观察均为空，已不显示 Required sources are unverified，外部依赖已勾选，仍给出泛化 Retirement is blocked...，无可定位的剩余对象或完成入口。
- 恢复：使用标签卡片的“仅移除策略定义与列出的引用”路径，来源校验后 Remove，再完整发布。server-v2 的策略定义已成功移除。该恢复不能证明完整退役检查通过。
- 证据：/Users/munmunmiao/Documents/web/headscale-ui/reports/usability-2026-10-26/ux03/evidence/16-empty-tag-retirement-still-blocked.png。

### UX03-F03：全部标签已选时，空建议文案误报未读取定义

- 严重程度：低，文案体验问题，不是写入失败。
- 前置条件：两个可用标签定义都已发布并读回；设备编辑器将这两个标签全部选中。
- 复现步骤：Edit tags 中依次选择所有已声明标签。
- 预期：提示“没有其他可选标签”或同等准确说明。
- 实际：每个已选项都显示 Declared in the last policy read，建议区却显示 No compatible tag definitions were read. Create or align the policy definition first. 容易使管理员误以为定义缺失而重复创建。
- 恢复：无需修改定义，继续正常完整集合审阅即可成功保存。
