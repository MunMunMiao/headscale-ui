1. 空资料打开控制台，看到 Choose a server profile。使用 Add server 填写名称、origin、管理 API key 和资料密码，保留 Remember this connection，执行 Save and unlock，进入零用户、零设备总览。资料密码的说明清楚指出它只加密本浏览器保存的 API key，不是 Headscale 用户密码。

3. 在 Auth keys 检查默认值：约七天到期，Reusable 和 Ephemeral device 默认均未勾选。首次使用共享 capture-key 捕获到了列表掩码前缀，真实客户端明确拒绝短 key；这属于实验工具错误，不计为产品失败。改用本人私有、限定生成结果区域的捕获方法后取得完整 key。
4. client-b 用可重复密钥接入并广告本人隔离目标 `10.42.0.19/32` 及 IPv4/IPv6 默认出口路由。client-a 最初由于过早捕获旧展示值也用了可重复密钥；两台真实设备由同一密钥接入，随后该密钥仍显示 Ready/Reusable。此过程不是有意预置数据，后续已查明、纠正。
5. 为 Alice 实际生成新的单次密钥，client-a logout 后使用该完整密钥接入，创建 Alice 的节点 3、地址 `100.64.0.3`。列表刷新后该密钥显示 Used、不可用于新注册。此前 operator 的旧节点 2 后续清理掉。
6. 真实运行无 auth-key 的 tailscale up，得到服务器注册请求。通过 Add device → Register pending device 输入真实请求，明确选择 Alice、确认 login-server 和设备可信管理通道，审批后客户端进入 Running。没有用假请求 ID 冒充 pending registration。

8. 真实验证子网目标隔离：client-a 直连目标失败，client-b 直连返回正确内容；client-a 经 Tailscale 代理在审批前失败，UI 审批 /32 后成功，撤销后相同请求再次失败。默认出口路由也完成成对审批、客户端选用及成对撤销，但隔离出口请求未成功，因此出口数据面保留受阻。
9. 将放行规则删除并发布显式 `acls: []`。client-a 到 client-b 相同 HTTP 目标的请求从成功变为失败。通过 UI 新建并发布放行规则后，同一请求恢复成功。没有把单独一次失败当成策略有效。

## 4. 已确认体验问题

### UX08-U1：迁移入口不能直接进入目标集合编辑

- 严重程度：中等体验问题，可绕行；不是已确认的后端标签写入错误。
- 前置条件：设备具有 managed 与 retained 两个标签，两个标签均已定义。
- 复现：Access controls → managed 的 Live tag maintenance → Migrate identity → Use an existing identity → Target tag 填 retained → Review device tags。
- 预期：进入完整目标集合审阅，或提供明确可继续编辑的入口，而不是丢失迁移上下文。
- 实际：URL 为 `/devices?node=3&popup=node&from=access`，只显示 Machine details、地址、现有标签和 Close，没有编辑或确认完整集合的控件。关闭后回到 Access，需要重新去设备页手动编辑。
- 证据：`/Users/munmunmiao/Documents/web/headscale-ui/reports/usability-2026-10-26/ux08/evidence/ux08-browser-events.jsonl`，2026-10-25T16:48:52.252Z。
- 恢复：手动 Machines → Actions → Edit tags，审阅完整集合，去掉 managed、保留 retained，服务器写入成功。
