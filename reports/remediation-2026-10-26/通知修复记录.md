第一版只在 host 可写范围内实现：host 的 effect 临时改写 `feedback.beginNotification` 并使用 Base UI 的内部订阅键观察固定 key。它已有真实浏览器 RED/GREEN，但协调者指出挂载顺序、共享方法恢复和内部 API 耦合不合适，拒绝了该方案。

## 真实数据链与当前最小实现

1. 页面刷新入口及分段重读调用 `useSnapshot.refreshByUser()`。
2. 它通过 `feedback.beginNotification({ isCurrent })` 创建独立 operation，在读取成功且仍属于当前请求/会话后显式发布 `{ tone: "success", title: "product.dataRefreshed" }`。
3. `useActionFeedback` 是固定 message key 仍可获得的项目自有边界；翻译之后的标题文字不能可靠表达业务语义。现在 `NotificationData` 增加唯一可选字段 `refreshGroup?: string`，只使用现有 operation ID，不携带业务对象、错误原文或秘密。
4. 只有非 mutation 的显式 `publish()`、固定 `product.dataRefreshed` key、`success` tone 且没有 description 时才生成/延续该标识。相邻成员共享首个 operation 的 ID 作为呈现批次，仍各自调用一次原始 `add`，各自使用自己的 toast ID。
5. 其他真正发布的通知均切断相邻批次。`publishMutation()` 继续执行原来的结果映射和一次发布校验，只显式排除刷新合并资格；即使写确认使用相同的 `product.dataRefreshed` 标题，也没有刷新分组标识。未成功发布、重复发布和旧 scope 不改变批次。
6. `clearAllActionFeedback()` 在关闭旧通知、通知业务订阅者之前清除相邻批次。原 `isCurrent`、mutation outcome 和业务 state 的含义均不变。
7. 分组成员通过公开 Toast `onClose` 和 `toastManager.close()` 关闭：先清空该组成员并退休当前批次，再关闭同组 ID，避免递归或重新加入已关闭批次。Base UI 继续负责每个根节点的退出和移除，没有额外的移除框架或共享方法包装。
8. host 仅消费 `data.refreshGroup`，使用每次渲染的 Set 选择最新代表行。所有成员仍保留真实 Toast.Root 生命周期；其他成员不可见/不可交互。原可见三行上限按呈现行计算，隐藏成员不会挤掉其他结果。ending 阶段保留原 limited 标记。

只读检查确认：生产通知的 `add` 入口仍只有 `useActionFeedback`，没有新造旁路发布入口。

## 已验证的行为边界

- 两个真实刷新成功只显示一行，但仍为两次独立 add、两个不同 operation ID，业务反馈快照保持不变。
- 错误、unknown、possibly-applied、confirmed+刷新失败和 confirmed 成功写通知都不合并；同文写确认也保持独立。
- 中间的错误/不确定结果切断批次，后来关闭它也不会把两侧成功行重新合并。
- 其他 success key、同 key 的 info/warning/error、带不确定 description 的 success 都不获得刷新标识，并切断相邻关系。
- 旧 scope、重复调用不创建通知，也不能污染批次；会话清理在订阅者发布新结果前退休旧批次。
- 四成员刷新组的点击关闭、toast Escape、viewport Escape 均退休全部真实成员，后续消息不会使隐藏成员复现。
- 合并成员不占用其他错误的可见位置；关闭刷新组不会误关其他结果或清除业务证据。
- 既有 modal、焦点、触摸、RTL、4 秒计时及 ending 生命周期测试全部保留并通过。
